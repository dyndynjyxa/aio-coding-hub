# Claude Desktop support

Claude Desktop is a separate AIO client identity (`claude_desktop`). It shares AIO's provider database, gateway, failover, request logs, usage and pricing infrastructure with the existing CLIs, but does not share Claude Code's `~/.claude` configuration. Providers and route order are independent of Claude Code.

## Compatibility and ownership

| Concern | Claude Code | Claude Desktop in AIO |
| --- | --- | --- |
| Gateway | `ANTHROPIC_BASE_URL` in `~/.claude/settings.json` | AIO-owned 3P profile with `inferenceGatewayBaseUrl` pointing at `/claude_desktop` |
| Provider choice | AIO `claude` route | AIO `claude_desktop` route; switching AIO providers does not rewrite Desktop files |
| Models | Claude Code model IDs and per-provider policy | Desktop's own model catalog plus exact mapping sources in the profile; per-provider policy maps each ID to an upstream model |
| Statistics | `claude` request logs and usage | Separate `claude_desktop` request logs, usage and cost |
| MCP | Claude Code config | Desktop's own `claude_desktop_config.json` in the 3P user-data directory (stdio servers only) |
| Prompts | `~/.claude/CLAUDE.md` | Desktop's global instructions, `local-agent-mode-sessions/<account>/<org>/memory/CLAUDE.md` in the 3P user-data directory |
| Skills | `~/.claude/skills` | Desktop's local skills plugin, `local-agent-mode-sessions/skills-plugin/<org>/<account>/` in the 3P user-data directory |
| Workspaces | Prompts, MCP and Skills | Prompts, MCP and Skills |

AIO follows its existing proxy model: the Desktop profile contains AIO's placeholder credential and points to the local AIO gateway. The gateway applies the enabled Desktop providers, route order, failover and model policies. AIO does not write an upstream provider's key or URL into Desktop's profile. A provider must accept Anthropic Messages requests at its configured URL; a model-name mapping alone does not convert API protocols.

Like the Codex catalog projection, the Desktop model list starts from the client's own catalog. Desktop caches its signed model catalog in `model-catalog/published.json` under the 3P user-data directory (`documentBytes` holds the base64 JSON document); AIO lists the `ccd` surface's `main` section models that are offered on `gateway`, in catalog order, so new Claude releases reach the menu without an AIO change. Exact (non-wildcard) mapping sources of routable Desktop providers are appended, as Codex does; wildcard sources only apply to listed models. When the catalog has not been cached yet, AIO lists `claude-sonnet-5`, `claude-opus-5`, `claude-fable-5` and `claude-haiku-4-5`. A model offers a 1M variant (`supports1m` in the profile, `supports_1m` in `/claude_desktop/v1/models`) when its catalog `runtime.max_input_tokens` is at least 1,000,000, the rule Desktop's own gateway discovery uses; models missing from the catalog get it when they are Opus, Sonnet or Fable models. 200k stays the default selection, and choosing 1M is left to the user as in Claude Code: the gateway does not filter providers for 1M requests, so a provider without 1M support returns its own error. Desktop's embedded Claude Code strips the `[1m]` marker itself and sends the `context-1m-*` beta header, which is forwarded unchanged; Desktop's direct one-shot requests send `<model>[1m]`, and the gateway strips that trailing marker for `claude_desktop` before provider model policy runs. The provider form's four family inputs store wildcard mappings (`claude-sonnet-*`, `claude-opus-*`, `claude-fable-*`, `claude-haiku-*`) in the generic mapping list, so every version of a family maps to the given upstream model; exact mappings take precedence. Gateway start and provider or route changes rewrite only the profile's model list, and Desktop reads it on its next complete restart; a catalog that Desktop downloads later reaches the profile on the next gateway start or provider change. AIO also serves `/claude_desktop/v1/models` locally from the same list. The first takeover or release of the profile requires a complete Desktop restart; switching providers inside AIO's already-active gateway takes effect without rewriting Desktop configuration.

## File resolution and rollback

The inspected Claude Desktop 2.2553.1.0 bundle reads `deploymentMode` and the config library only from its 3P user-data directory. AIO resolves that directory as `%LOCALAPPDATA%\Claude-3p` on Windows, `~/Library/Application Support/Claude-3p` on macOS and `$XDG_CONFIG_HOME/Claude-3p` (default `~/.config/Claude-3p`) on Linux. Desktop 2.7032 uses `CLAUDE_USER_DATA_DIR` as its 3P directory on every platform, so if AIO's process environment sets it to an absolute directory, AIO uses that directory for 3P files on every platform too. A custom directory passed only to the Desktop process cannot be inferred by AIO; both processes must receive the same override, and the resolved path should be checked in AIO before enabling takeover. The 1P user-data directory (`%APPDATA%\Claude`, or the MSIX `LocalCache\Roaming\Claude` directory) is never read for `deploymentMode`, so AIO does not write it.

Enabling the Desktop proxy backs up and then updates exactly these files:

1. The 3P `claude_desktop_config.json`: set only `deploymentMode` to `3p`.
2. The AIO-owned `configLibrary/00000000-0000-4000-8000-000000a10d35.json`: write the gateway profile.
3. `configLibrary/_meta.json`: add the AIO profile entry and select it.

The proxy manifest and original bytes live under AIO's own app-data `cli-proxy/claude_desktop` directory. Disabling restores the previous deployment mode (and the 1P file for manifests created by earlier AIO builds that also wrote it) and previously selected profile where it still exists, removes only AIO's profile entry, and preserves unrelated profile entries, MCP servers and preference changes made while AIO was active. Invalid existing JSON is rejected before any profile write.

Desktop MCP management targets the 3P `claude_desktop_config.json`. AIO does not create or rewrite that file during unrelated global MCP refreshes until at least one Desktop MCP server is managed by AIO. Desktop only loads stdio servers (`command`, `args`, `env`) from this file, so enabling an HTTP/SSE server in a Desktop workspace fails with an error and the file is left unchanged. AIO does not use `managedMcpServers`, because Desktop then puts its Code tab into strict MCP mode. Changes take effect after Desktop restarts. Known limitation: a running Desktop can write stale content back to the same files. AIO also writes them on its own, on gateway start, proxy toggles, exit and workspace sync, so it cannot require Desktop to be closed first; like Claude Code's `~/.claude.json`, AIO does not detect the running app. A server disabled while Desktop was running can come back as a local entry that AIO no longer manages; remove it in Desktop.

Desktop Prompts and Skills live under `local-agent-mode-sessions` in the 3P user-data directory. The account comes from the base64 UUID in `ant-did` and the organization from the applied profile's `deploymentOrganizationUuid` (default `00000000-0000-4000-8000-000000000001`), so Desktop must have been started once with the current profile before AIO can manage them. The global-instructions directory uses the first 8 characters of both IDs; AIO uses the full IDs only when the short directory is missing and a full-ID directory exists. Enabled Skills are copied (not linked) into the skills plugin's `skills/` directory and listed in its `manifest.json` as `creatorType: "user"`, `syncManaged: false`; Desktop deletes skill directories missing from the manifest. Built-in Desktop Skills and entries AIO does not own are kept. The Code tab loads this plugin as well as `~/.claude/skills`, so a Skill enabled for both Claude Code and Desktop appears twice there. Desktop global instructions do not reach the Code tab. Changing the Desktop profile to another organization moves both directories; AIO does not move existing Skills to the new location.

The implementation follows the installed Desktop bundle's `deploymentMode` and `configLibrary` behavior and uses CC Switch's Desktop profile implementation as a format reference. It deliberately keeps AIO's own gateway and provider route architecture instead of CC Switch's proxy pipeline.
